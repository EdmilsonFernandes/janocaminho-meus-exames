## Description

The image-processing library sharp is pinned to 0.32.6, which bundles libvips, libheif and librsvg builds affected by multiple published memory-corruption advisories (GHSA-f88m-g3jw-g9cj, GHSA-rgj7-g3m4-5g8c, GHSA-wq5f-xc86-pv6w). This application processes attacker-supplied images with this exact version on its upload endpoints.

## Evidence

**Advisory evidence:** `CVE-2026-33327` applies to `sharp` at installed version `0.32.6`. The advisory is fixed in `0.35.5`.

**Transitive dependency:** introduced by the direct dependency `sharp@0.32.6`.

**Dependency chain:** `sharp@0.32.6`

**Usage analysis:** the advisory's affected API is used in application code. Source-to-sink trace: POST /api/patients/:id/photo (src/routes/patient.routes.ts:321, multer upload.single) → savePatientPhoto (src/utils/storage.ts:108) → optimizeAvatar (src/utils/imageStorage.ts:11) → sharp(buffer, { failOn: 'none' }).resize().jpeg().toBuffer(). Same sink reached by POST /api/doctor/me/photo (src/routes/doctor.routes.ts:444 → src/utils/storage.ts:143), by POST /api/exams file upload (src/routes/exam.routes.ts:151 → saveExamFile → src/utils/storage.ts:159), and by POST /api/medications/scan-photo (aiLimiter-gated but open to any authenticated user). 'failOn: none' at imageStorage.ts:11 explicitly instructs sharp to keep processing malformed images, i.e. the hardened bail-out is disabled on every attacker-reachable path. No image source is trusted-only. This is a prioritization signal from static analysis, not a proof of exploitability or of safety.

## Impact

An authenticated user (any account — registration is open) uploading a crafted image (avatar/photo/exam scan) can trigger memory corruption in the image-decode pipeline. Demonstrated consequence class: process crash (event-loop death → API-wide DoS). Upper bound per advisories: potential RCE on glibc Linux, which would expose the PostgreSQL database holding LGPD-sensitive health data (CPF, exams, mental-health screenings).

## Contextual CVSS

sharp 0.32.6 is imported at src/utils/imageStorage.ts:1 and optimizeAvatar() at src/utils/imageStorage.ts:11 calls sharp(buffer, { failOn: 'none' }) on raw upload bytes. The path from the network to this sink is direct: POST /api/patients/:id/photo (src/routes/patient.routes.ts:321, upload.single('photo') → savePatientPhoto → src/utils/storage.ts:108 optimizeAvatar), POST /api/doctor/me/photo (src/routes/doctor.routes.ts:444), exam uploads (POST /api/exams, src/routes/exam.routes.ts:151 upload.single('file')) and POST /api/medications/scan-photo — all require a valid patient/doctor JWT (privileges_required:L), which is freely obtainable via open signup. 'failOn: none' disables sharp's own malformed-input bail-out, widening the accepted input class for libvips/libheif/librsvg image-parsing bugs. In this codebase the demonstrated consequence class is memory corruption in the image pipeline (crash: A:H) with best-case code execution (C:L/I:L scored conservatively; the GHSA upper bounds are higher but require runtime confirmation). Advisory base is CVSSv4 AV:L/PR:L (8.9) because upstream assumed a local file; this deployment feeds it network-sourced authenticated uploads, so attack_vector:N is the honest contextual rating.

## Remediation

Upgrade sharp to >= 0.35.5 (fixes GHSA-wq5f-xc86-pv6w / CVE-2026-96889, which also covers the libvips CVE-2026-33327/33328 and libheif fixes shipped in 0.35.0/0.35.4). Additionally remove `failOn: 'none'` so malformed images are rejected early, and run image decoding in a disposable worker/queue so a crash cannot take the API process down.

## Assumptions

Advisory data verified against the trivy-offline GHSA database (web search unavailable in this sandbox); installed version 0.32.6 confirmed from node_modules. Exploitability assumes attacker can upload an image through any authenticated upload endpoint (patient photo, doctor photo, exam file, medication photo scan).
