# Jobs to Be Done — Dr. Exame

## Framework

O usuário não quer "ver exames" — quer saber se precisa se preocupar.

### Três dimensões de job

**Funcional** (tarefa prática):
- O que o usuário está tentando ACCOMPLISH?
- Ex: "Entender se meu exame está ok" ≠ "ver resultado de TSH"

**Emocional** (como quer se sentir):
- O que o usuário quer SENTIR?
- Ex: "Sair da ansiedade do aguardo" ≠ "receber notificação"

**Social** (como quer ser percebido):
- O que o usuário quer que outros pensem?
- Ex: "Ser um pai que cuida da saúde da família" ≠ "enviar exame do filho"

## Como aplicar no Dr. Exame

### Para o PACIENTE
```
Quando [situação], quero [motivação], para que [resultado esperado].

Ex: Quando recebo um exame do laboratório, quero entender
se os valores alterados são graves, para que eu saiba se
preciso marcar consulta urgente ou posso esperar.
```

### Para o MÉDICO
```
Ex: Quando atendo um paciente novo, quero ver o histórico
completo de exames com tendências, para que eu não perca
15 minutos perguntando o que ele já fez.
```

### Descoberta

1. Ler feedback de usuários (tickets, reviews, suporte)
2. Identificar VERBOS de ação ("quero saber", "preciso entender")
3. Mapear ANSIEDADES ("será que está grave?")
4. Identificar momentos de "contratar" o produto
5. Verificar: qual job o produto resolve HOJE vs qual DEVERIA?

## Output

Para cada job identificado:
```
| Job (funcional) | Emocional | Social | Como o app resolve hoje | Gap |
```

## Uso
- **Posicionamento**: "O app que tira a ansiedade do exame" > "gestão de exames"
- **Landing page**: falar do JOB, não da feature
- **Priorização**: features que resolvem o job principal primeiro
