Arquitetura de Agentes, Skills & MCP

Você tem 119 skills ativas, 461 agentes dormentes e ~15 servidores MCP globais carregando contexto em toda sessão. O problema não é quantidade — é que tudo paga imposto de contexto o tempo todo. Este é o plano de mercado para organizar em camadas, com orçamento de contexto explícito.

02

O modelo mental (consenso de mercado 2026)

Skills

expertise · procedimento
  • Só a descrição carrega no boot (~40 tok cada)
  • Corpo entra só quando invocada — progressive disclosure
  • Portátil: serve pra qualquer repo
custo: ~0 até o gatilho

MCP

acesso · ferramenta
  • Expõe sistemas externos: DB, GitHub, browser
  • Schema + instruções carregam em todo turno
  • Substitui hallucination por dado real
custo: fixo por sessão inteira

Subagents

isolamento · paralelismo
  • Contexto próprio — não polui a thread principal
  • Rodam em paralelo (exploração, revisão)
  • Podem usar skills e MCP dentro deles
custo: 0 na thread principal

Não competem — combinam: MCP dá acesso, skill dá conhecimento, subagent dá mão de obra isolada. A orquestração hierárquica (arquiteto → verificador → executor) é o padrão generator-verifier / orchestrator-subagent da Anthropic.

04

As seis regras da casa

R1
Contexto é orçamentoNo boot só entra o que serve a TODO projeto. Tudo else paga sob demanda — ou morre arquivado com catálogo.
R2
Skill global = cross-project com gatilho claroSegurança, docs Office, AWS, e-mail, dev-workflow núcleo. Skill de domínio (analyze-token, health-review…) vive no repo que a usa: .claude/skills/.
R3
MCP global só o universalgithub + context7 (e playwright, se usar em tudo). O resto — wibx-*, biomcp, planner, ui-expert, web_reader — vira .mcp.json do projeto dono. O repo de exames para de pagar pelos 10 Postgres do Wibx.
R4
Revisor é subagent, não skillui-reviewer, a11y, security, perf do Dr. Exame viram .claude/agents/*.md do repo: contexto isolado, rodam paralelos, retornam veredito.
R5
Generator → verifier sempreNada é "pronto" sem passar por um gate: /gate (UX 44 checks), code-review nativo, CI (o exemplo maduro que já funciona no seu deploy). O crítico adversarial (/critique) argumenta pela REJEIÇÃO.
R6
Arquivo organizado é bibliotecaskills-archive + catálogo + agents-library como estoque: reativar por mv quando o trabalho pedir. Morto é o que carrega sem ser usado.

Plano de 30 dias

Semana 1 · maior ganho
MCP hygiene + poda de skills

Mover 10+ servers globais para .mcp.json dos projetos donos (wibx-* → repo wibx; biomcp → exames). Podar skills globais 119 → ~50 arquivando as de uso raro. Economia imediata em TODA sessão de TODO projeto.

Semana 2
Revisores viram subagents + gates no fluxo

Converter ui-ux-reviewer, accessibility-reviewer, security e perf do Dr. Exame em .claude/agents/. Instituir: todo PR passa dev → /gate + code-review antes do "pronto".

Semana 3–4
Pipelines determinísticos + medição

Workflows para rotinas repetitivas (review pipeline, release). Medir com /caveman-stats e rtk gain: tokens/sessão antes vs depois — o placar valida a arquitetura.
